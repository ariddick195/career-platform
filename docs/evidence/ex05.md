# Exercise 05: Investigate a DNS or TLS Failure

## 1. Setting and prediction

A supplied simulation was used in the investigation, not a personal live website, and `site.lab.example` is supposed to reach a new Railway deployment through the routing target `current-app.up.railway.app`, with Cloudflare managing its DNS. I expected the hostname to resolve to the Railway destination and HTTPS to work with a valid certificate for `site.lab.example`.

## 2. Failed check and evidence

October 13, 2026

From simulated DNS and HTTPS results, The DNS check command `dig site.lab.example A +noall +answer` returned:

site.lab.example. 300 IN A 198.51.100.24

Result shows the old Azure server address, instead of the expected Railway destination.

The HTTPS check command `curl -Iv https://site.lab.example/` resulted in:

* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name


Result shows a certificate for `old-vm.lab.example` that did not match `site.lab.example`, resulting in a certificate verification error (curl error 60).

## 3. Diagnosis

The problem was caused by the DNS record still pointing to the old Azure server instead of the new Railway deployment. Because the hostname connected to the old server, it received a certificate for `old-vm.lab.example` instead of `site.lab.example`. This caused the HTTPS check to fail because the certificate name did not match the hostname being accessed.

## 4. Repair and repeated check

The simulated repair involved changing the old A record for `site.lab.example` to a CNAME record pointing to `current-app.up.railway.app`, which is the Railway routing target. The purpose of this change was to direct the hostname to the correct deployment instead of the old Azure server.

After the simulated change, the DNS check returned:


site.lab.example. 300 IN CNAME current-app.up.railway.app.
current-app.up.railway.app. 300 IN A 203.0.113.44


The HTTPS check then connected to `203.0.113.44` and verified the certificate for `site.lab.example` successfully. The request returned HTTP/2 200, showing that the simulated repair corrected the DNS destination and certificate mismatch.

## 5. What you learned

This investigation showed me how DNS records affect which server a hostname reaches and how HTTPS certificates are used to verify a website's identity. I learned that a website can have a DNS record that resolves successfully but still fail its HTTPS check if it reaches the wrong server. I also learned that after repairing a DNS record, it is important to repeat both the DNS and HTTPS checks to confirm that the problem has been resolved.
