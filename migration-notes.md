## Plan deviations and rulings

1. **EC2 size and CPU architecture:** the plan's low-cost Graviton `t4g.micro` choice was rejected by the account's explicit `ISBA4775EC2Migration` policy, which permits only `t3.micro` and `t3.small`. Used the allowed `t3.micro` and matching Amazon Linux x86_64 image. This preserves the account guardrail but is a little more expensive and provides less memory than the intended Graviton host.
2. **Operator access:** initial Session Manager access was denied. Added a narrowly scoped operator policy for the named EC2 instance and corrected the self-session ARN variable; Session Manager now works. No SSH ingress was opened.
3. **Source data gate:** a fresh Railway PostgreSQL backup exists outside the repository and restored successfully into disposable local PostgreSQL 18.6. Its Alembic revision `0001_initial_schema` matches the repository's only migration head. All seven child tables have zero null and zero dangling `person_id` values. The schema defines `person_id` columns without database foreign-key constraints, so application references were checked manually. The later restore entry below records the approved restore to RDS and matching verification. Do not cut over DNS until application-level validation and the remaining deployment gates pass.
4. **Budget gate:** partially resolved, not passed. The owner reports the AWS Credits console showed three active credits: $20 “Explore AWS: Set up a cost budget using AWS Budgets,” $20 “Explore AWS: Create an Aurora or RDS database,” and $100 “AWS Free Tier.” Console totals reported: $140.00 total remaining, $0.00 total used, $139.59 estimated remaining, and $0.41 estimated used. Each credit expires 2027-10-29. The owner-provided text said each applies to “See complete list of services”; exact service eligibility and credit application to this stack remain unverified. `isba-student` cannot call Cost Explorer (`ce:GetCostAndUsage`) or AWS Budgets (`budgets:ViewBudget`), and the installed AWS CLI does not provide `aws billing list-credits`. Current charges and existing budget alerts therefore remain unverified. The approximately $20/month cap remains ambiguous as gross AWS charges versus out-of-pocket after credits. EC2 and RDS are running and accruing charges; do not treat this gate as passed.
5. **Network access:** used the existing default VPC and RDS security group rather than creating a separate RDS security group. Tightened the default group's inbound rules to match the plan: only PostgreSQL from the EC2 app security group.
6. **EC2 secret-bootstrap verification path:** the user reported that customer-managed policy `CareerPlatformRdsSecretBootstrapTemporary` was created under IAM Policies and attached to `career-platform-ec2-ssm`. The operator identity cannot inspect that role's attachments, but a functional on-instance test has confirmed `secretsmanager:GetSecretValue` succeeds for the RDS-managed secret without displaying its value. The attachment itself remains unverified through IAM listing APIs.
7. **Session Manager operator scope:** the existing `isba-student` policy initially permitted a default interactive shell on the named EC2 instance but not `ssm:SendCommand` or `ssm:StartSession` for the AWS-managed `AWS-StartInteractiveCommand` document. After the user added `arn:aws:ssm:us-east-1::document/AWS-StartInteractiveCommand` to the existing `ssm:StartSession` resource list, the non-secret EC2 checks ran successfully through that document. No `ssm:SendCommand` permission was added.

A separate Ed25519 key was later generated and registered with the owner's approval; the Railway CLI private SSH tunnel then succeeded and the backup was created and tested (see activity log). The original key/passphrase remain unverified. Do not put any key passphrase in notes or chat.
9. **Restore/migration ordering:** the owner explicitly directed that the Railway PostgreSQL backup be restored to RDS before running application migrations. This differs from Phase 3 of the original plan, which lists applying Alembic migrations to empty RDS before the restore. The backup's Alembic revision `0001_initial_schema` matches the repository's only migration head. The approved restore to the existing RDS instance completed and was verified on 2026-11-10 (see activity log). No application migrations or seeds have run. Never seed production.
